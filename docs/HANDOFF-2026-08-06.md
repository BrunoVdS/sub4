## 4. D5's remaining three slices

**`lifecycle_event` / `lifecycle_line` — HALF BLOCKED, and this is new.**

Two problems, both established this session:

1. **There is no store to import from.** The other four slices read a JSON
   file. Lifecycle receipts live in `LifecycleLog.shared` in memory and persist
   nowhere — which is why the table exists. So the receipt has to be written
   *at the moment the operation completes*: write-through, arriving early for
   one table, ahead of D6b.
2. **The disconnect receipt cannot be written at all.** Patch 281 made
   `.database` `.removeEverything` on disconnect, so a `disconnect` receipt
   written to the database is destroyed by the operation that wrote it — the
   same incoherence patch 186 identified for delete receipts, which is why
   `operation` is constrained to `('export','disconnect')` and refuses
   `delete`. It becomes writable when 282 removes rows instead of the folder.

So: **export-only now, or park until 282.** Recommendation is park — it would
otherwise be built twice, and the export half alone is low yield.

**`review_evidence_source`** — blocked until a review exists (24 August).

**`content_revision`** — still unsettled. The four backfill flags and three
schema versions are build markers, not content hashes. The plan's content hash
was proposed and withdrawn: the migration comment says the table is for
skipping unchanged content on re-import, and that job is already done three
ways. **Settle before building.** Note the peer review independently proposed
the same withdrawn answer, which suggests the table's *name* invites it.

**Four preference keys are staying**: `appearance.selected`,
`discipline.selected`, `volume.unit`, `zones.window`.

## 6. D6a design notes — established 6 August, do not re-derive

**The `activity` table DOES round-trip a full `Activity`.** The five fields
missing from the original schema were added by `Sub4Migrations+Inputs`. But
five names differ, and one of them is a trap.

| `Activity` | column | note |
|---|---|---|
| `id` | `activity_source_record.externalID` | **`activity.id` is a minted UUID.** The store's id is Strava's, and it is reached through the source record, not the primary key |
| `sportType` | `sportLabel` | nullable — a hand-entered activity has none |
| `distance` | `distanceM` | |
| `movingTime` / `elapsedTime` | `movingSeconds` / `elapsedSeconds` | |
| `elevationGain` | `elevationGainM` | |
| `startLat` / `startLon` | `startLatitude` / `startLongitude` | |
| `isTrainer` | **`isIndoor`** | renamed deliberately — see the Inputs migration header |
| `deviceWatts` | **`hasPowerMeter`** | likewise |
| `maxSpeed` | `maxSpeedMS` | |
| `gearId` | **`gearID`** | **THE TRAP: the column holds the CANONICAL gear id, the store holds Strava's.** Reconstituting an `Activity` faithful to the JSON needs a mapping back through `gear`. Get this wrong and shadow parity reports divergence on all 479 gear-bearing activities, for a reason that has nothing to do with the data |

Also on the table and not on `Activity`: `accountID`, `dayKey` (stored, not
derived), `discipline` (checked vocabulary), `createdUTC`, `updatedUTC`.

**Nothing in the app reads the database yet.** `Sub4Launch.swift` line 33 says
so. Eight files reference `Sub4Database` and the only view among them is
`DatabaseHealthView`.

## 7. The lesson this session kept teaching

Four instances of one pattern, and it earned its keep every time:

- `StoreLoad` (§12.15) — a file that could not be read vs a file that is absent
- `Reading` (§12.28.3) — a Health query that failed vs a Health store that is empty
- `RouteCensus` (§12.32.4) — five named causes for one measure inside it
- `hasRoute: Bool?` (§12.31.3) — `nil` means nobody asked

**The instrument was wrong three times in one evening and never lied once.**
With `[]` in place of the optional, the first census run would have reported
*"none of the 53 has a route"* — quotable, plausible, and false by five.

Two related rules, both earned:

- **A prediction is not a trigger** (§12.27). `.database`'s gap predicted its
  own correction and nothing noticed when the moment arrived. Couple the claim
  to the thing that would falsify it — and pick something that *changes by a
  person's deliberate act*, so it fires in front of somebody already thinking
  about it.
- **Prose in a `View` goes stale silently** (§12.34). Compute the sentence from
  the data, as `DataLifecycle.summary` does. Pin the *absence* of a
  hand-written list, not the presence of the right one.

## 9. Working rules

- Patches unzip into `~/Documents/Developer/sub4/Sub4/Sub4/`; tests into
  `Sub4CoreTests/`; repo-level files into `~/Documents/Developer/sub4/Sub4/`.
- **Never** use Xcode's "Add Files" — file-system-synchronized groups. A **new**
  file needs ⌘Q and reopen, or its tests silently never run. That happened to
  patch 280's whole suite and was only noticed when the count didn't move.
- **Nothing that is not Swift source** goes under `Sub4/Sub4/`.
- `AppVersion.swift` ships in **every** patch — numbered patches bump `patch`
  and set `revision` to nil; letter fix-ups keep `patch` and set `revision`.
- **Run the suite before ⌘R.** ⌘R compiles the app target only; test-target
  errors accumulate invisibly. It is also the only compiler in the loop.
- Every apply script reads `SUB4_ROOT` from the environment so it can be
  preflighted against a byte-exact copy before shipping.
- `git --no-optional-locks status` — plain `git status` leaves an index lock.
- A stray paste into a source file is `git checkout -- <file>` and nothing
  more, provided every patch went through git before the next one started.
